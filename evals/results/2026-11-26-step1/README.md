# 第 1 項實驗紀錄 · 2026-11-26

本次建立單模型基準，回答兩個問題：評測器能否保留失敗與缺圖的真實狀態？菜名通過模糊配對時，整筆品項和價格是否正確？同批固定輸出可供日後比較解析方式及雙模型複核。產品程式、提示詞與推薦規則沿用實測當時版本。

## 資料及條件

舊開發集四份答案共 131 項，目前只有向宏原圖可取得。不倒翁（8 項）、斗六門（35 項）、國紹（64 項）共 107 項缺圖。原始套件可執行 1/4，本次另取兩家店公開菜單各一個完整 PDF 跨頁。兩頁以 Poppler 26.11.0 轉為長邊 1900 像素的 PNG，在首次呼叫模型前逐項核對並凍結真值。六筆已登錄案例中指定三張有原圖者實跑，共 60 項、59 個固定價格及 1 個時價。這批是開發階段的基準，後續獨立測試集需使用其他餐廳或版型。

- 大來小館麵湯頁為原 PDF 第 2 頁（印刷頁碼 3–4）。相同價格的斜線選項按印刷品名計一列；有三種明確價位的湯拆成小、中、大。照片說明重複品項只計一次，鮮海魚湯的時價真值為 null。[大來小館原始菜單](https://www.dalaifood.com.tw/images/menu.pdf)
- 名人堂花園大飯店台灣小吃總匯套餐頁為原 PDF 第 2 頁（印刷頁碼 2–3）。按可點購的五個套餐計分，套餐內含料理及換飲說明均不另計。[飯店原始菜單](https://hotel.fhgh.com.tw/download/0/202/)

兩個來源、取得日、PDF 與輸入影像 SHA-256、取頁方式、標註時間及逐項答案都在對應的 `*.expected.json`。擷取當日的 PDF 已另存於本機 `evals/menu_ocr/runs/source-pdfs/`，實測影像位於 `evals/menu_ocr/cases/`，均依專案慣例保存在本機。要從來源重建時，以 `pdftoppm -f 2 -l 2 -scale-to 1900 -singlefile -png <來源PDF> <案例路徑不含副檔名>` 產圖，再核對真值檔內的 `inputSha256`。

## 實測數據

校內模型端點使用 ornith-35b，每張完整影像單次辨識，單工依序執行。時間為評測器觀測到的每張處理時間，未包含手機裁切與人工確認。正規化後的完全匹配忽略標點差異。最後一欄前的數字只統計有標價的品項；完整列則也包含時價是否保留未知。逐案設定與原始回應見 [live 紀錄](ocr-live.json)。

| 實際輸入 | 模糊配對，門檻 0.72 | 菜名與價格狀態均正確 | 正確固定價格 | 處理時間 |
|---|---:|---:|---:|---:|
| 大來小館麵湯頁 | 31/31 | 31/31 | 30/30 | 65.5 秒 |
| 名人堂小吃套餐頁 | 5/5 | 5/5 | 5/5 | 25.3 秒 |
| 向宏魯肉飯 | 24/24 | 22/24 | 22/24 | 2.2 秒 |
| 合計（逐品項） | 60/60 | 58/60（96.7%） | 57/59（96.6%） | 93.0 秒 |

- 向宏的「（限內用）75套餐」與「（限內用）85套餐」都漏了「限內用」，價格回傳 null。原圖把 75／85 寫在套餐名稱中，沒有在旁邊另列獨立數字價格。這兩筆依既有真值列為漏價，保留原標註供複查。兩筆相似度均約 0.727；把門檻從 0.72 提至 0.75，總配對數由 60 降至 58，完整列維持 58。0.72 下計入漏抓與多抓的正規化字元錯誤率為 2.24%。[完整門檻掃描與資料盤點](diagnostics.json)
- 向宏的資料完整度分數為 0.954，但仍有上述兩筆錯誤。大來小館唯一的時價品項正確保留未知。本次兩張網路頁面均為清晰的電子排版，這批數據可檢查套餐、規格價與時價，對現場反光與皺摺的表現仍需另測。
- 向宏在舊版評測器的首次 live 呼叫為 53.5 秒，新版再送為 2.2 秒。兩次回傳的模型文字 SHA-256 完全相同，原始圖與產品策略相同。服務端快取狀態未知，這兩個延遲保留為觀察值，不能推算評測器的加速倍率。[舊版原始紀錄](ocr-legacy-xianghong.json)
- 三張 live 各觀察到一次 urllib 請求。離線重播的三張結構化品項與 live 逐項相同，並觀察到零次 HTTP 請求。離線重算可直接使用真值快照與解析輸出，不需原始服務。[重播紀錄](ocr-replay.json)
- 本機推薦規則回歸執行 10 個既有情境，通過 10、失敗 0、略過 0。存檔包含案例、菜單快照、解析偏好、實際推薦與規則門檻，用以日後區分推薦邏輯及評分規則的改變。滿意度未測。[推薦逐案結果](recommendation.json)

## 重算與核對

在專案根目錄的 PowerShell 執行下列命令。前兩項是離線重算及門檻掃描；第三項需要本機案例圖片，可用已記錄的回應重播。建議優先從封存回應重算以免花費 API 額度。

```powershell
$run = 'evals/results/2026-11-26-step1/ocr-live.json'
.\.venv\Scripts\python.exe -X utf8 evals/menu_ocr/run_eval.py --rescore $run
.\.venv\Scripts\python.exe -X utf8 evals/menu_ocr/run_eval.py --sweep $run
.\.venv\Scripts\python.exe -X utf8 evals/menu_ocr/run_eval.py --replay $run --case xianghong --case web_dalai_noodles_soups --case web_fhgh_sets --label verify-replay
```

需要重新觀察校內模型時，用相同三個 `--case`、`--debug` 及新標籤執行 live。新 run 會保存程式與資料雜湊、請求設定及服務別名；後端權重版本與快取狀態以服務能提供的資訊為限。專用評分測試涵蓋成功配對內指標與全真值分母、整張失敗、缺圖、空輸出、重排同分及離線重播。完整測試在隔離工作副本以模擬 API 設定執行，330 項通過。

後續交叉比對可從這份單模型基準出發，在其他開發菜單選定「觸發第二模型」的條件，再比較額外呼叫數、修正的錯誤、誤改與待確認數。兩模型各給一個答案而意見不同時為平票，需要保留分歧或獨立依據。該機制尚待實驗。
