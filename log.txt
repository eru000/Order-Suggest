一、第一項解決了什麼
期中報告第 4.1 節以菜名相似度 0.72 配對。這能回答「系統是否找到了這道菜」，但一道菜即使配對成功，仍可能漏掉內用限制或價格。本次把「找到品項」、「菜名逐字正確」、「菜名與價格狀態皆正確」分開計算，並保存每次辨識的輸入、回應與評分設定。沿用既有模型、提示詞與推薦規則，以便日後在相同條件下比較。本次實測已找到兩筆會影響點餐的錯誤，詳見第四節。

二、程式與評分方式
1. 評測流程會分別登錄成功、空輸出、執行失敗與缺圖略過。已送測的案例即使失敗或沒有辨識出品項，其已知標準答案仍納入分母；缺圖另列在資料盤點，避免將無法送測誤算成模型漏抓或測試通過。
2. 菜名配對先統一英文大小寫，保留中文字、英文字母及數字，去除標點與空格。使用 Python 的 difflib.SequenceMatcher.ratio() 計算相似度；若字元及各字出現次數都相同、僅順序不同，相似度記為 1。依分數由高到低做一對一配對，同分優先配對正規化後完全相同的菜名。「菜名完全正確」仍要求字序相同。
3. 模糊配對分別計算召回率（配對數／標準答案數）與精確率（配對數／預測數）。「完整列正確率」以所有送測品項為分母，要求正規化菜名完全相同，且數字價格相同或正確保留時價未定。「固定價正確率」以標準答案中所有固定價品項為分母。嚴格字元錯誤率（CER）以標準答案的正規化菜名總字數為分母，計入替換、插入、刪除，以及整個漏抓或多抓的菜名。
4. 評分版本為 menu-ocr-score-v2。執行紀錄保存案例清單、圖片及標準答案的 SHA-256、程式雜湊、模型設定、原始回應與解析結果，可用同一批輸出離線重算分數。推薦規則評測也分開記錄通過、失敗及略過，並保存當時的菜單、偏好與推薦結果。

二、改了什麼
1. 新增 src/menu_price.py 的 parse_price，照片辨識（menu_vision）與爬蟲匯入（menu_ingestion_service）改用同一套規則。只有確定是單一明確價格才轉成數字；其餘保留狀態與原文，狀態分為 fixed、market（時價）、range（範圍、約略價、起價）、multi（一格多價）、unreadable（含 ? 等無法辨識字元）、missing。
2. 品項保留原本的 price 欄位（只有 fixed 才有數字），另增 priceInfo 記錄原文、狀態與原因，推薦器與評測器不需修改。人工以「改 N 價格 X」修正後，priceInfo 標為人工修正。
3. 一格多價且每個價格都有標籤時（如「大60/小45」），拆成「乾麵（大）」「乾麵（小）」兩項，與提示詞要求及真值標註方式一致；沒有標籤則保留一項、價格未知。
4. 同名不同價（如「乾麵 45」「乾麵 55」）原本第二筆被丟棄且無任何提示。現在仍保留第一筆，但記成價格衝突，確認畫面會列出，存檔前須明確接受。前端衝突說明文字一併修正，原文案「在重疊區辨識到不同價格」是舊切塊架構的用語。
5. 數字 0 維持原行為，沿用推薦器「price == 0 視為時價」的既有慣例。

三、修改前的實際行為（以原程式函式直接執行確認，非推測）
輸入「1?0」得 1.0 元、「$ 9?」得 9.0、「100～190」得 100.0、「大60/小45」得 60.0、「約150」得 150.0。其中「1?0」被當成 1 元，在預算篩選中會因最便宜而被優先選入。同名不同價以「乾麵 45／乾麵 55」最小輸入重現，只剩 45 且 warnings 為空。

4. 前端用語：「辨識品質良好／尚可／偏低／很低」改為「資料完整度高／尚可／偏低／很低」，因為該分數只反映價格欄位填寫比例與品項數，不代表辨識正確。另加「N 項待確認」標籤；待確認品項的價格欄顯示原文（例如「待確認：1?0」），不再一律顯示「價格不明」。分數公式與 0.75 門檻未改。
5. 資料庫寫入價格時的第三套解析（storage/repositories.menu_price）改用同一個 parse_price，三處解析規則一致。

2026-11-27｜第四項（續）　修正「取消條件」：第二項開發情境 dev_cancel 的兩個錯誤

2026-11-27｜第五項（開發階段）　OCR 基線（A 組）與 VLM＋OCR 交叉複核（D 組）

一、做法
• A 組 OCR＋版面配對（evals/menu_ocr/ocr_baseline.py）：OCR 引擎為 RapidOCR 1.4.4。它是 PaddleOCR 的 PP-OCR 偵測與辨識模型轉成 ONNX 版本，以 CPU 執行。PP-OCR 中文模型常輸出簡體字形，因此先以 OpenCC s2tw 轉回繁體。之後以版面規則把文字行配成「品名＋價格」：同一列右方最近、中間沒有隔著其他品名的價格；規格與價格同一行（小90 中160 大240）拆成規格品項；括號小字註記接到下方品名前；中英對照時去掉英文翻譯；字級明顯較大的標題才往下找價格；沒配到價格且字級較小的行視為說明文字。規則只用開發資料設計，共四版，每版都是通則，沒有針對個別菜單的特例。
• 評測器新增 --method ocr，與 VLM 共用真值、配對、計分及紀錄。專案 Windows 環境為 Python 3.14，PaddlePaddle 不一定能安裝；因此 OCR 在使用者電腦上的 Linux 環境以 Python 3.12 執行，依賴列於 evals/menu_ocr/requirements-ocr.txt，不加入產品依賴。
• D 組交叉複核（evals/menu_ocr/cross_check.py）：VLM 負責擷取，OCR 只用來找疑點，不修改 VLM 的輸出。標記分四種：price_ambiguous（價格看不清、範圍或多價）、name_not_in_ocr、ocr_price_mismatch、price_unverified（VLM 有價格、OCR 在該品名旁讀不到）。另回報 orphans，即 OCR 讀到「品名＋價格」但 VLM 沒有的項目。VLM 端重播第二項第 1 輪以 --debug 保存的原始回應，以目前的解析器解析，不打 API。
